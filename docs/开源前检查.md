# 开源前检查记录

检查日期：2026-10-17。检查基线：`c310f68`，以及本次新增的 README 和许可证说明。

结论：项目可以继续整理为公开仓库，但目前不建议直接宣称“安全、开箱即用、可公网部署”。本次完成文档和许可整理，没有修改认证、消息采集或权限策略；下面的未处理事项仍然存在。

## 检查范围

- 当前 Git 跟踪的 124 个文件，包括 Python 服务、dsh 接入、管理端、部署配置、测试和文档。
- 本地所有 Git 引用可达的 90 个提交，检查提交路径和补丁中的常见凭据模式。没有对远端未知引用或未拉取对象作保证。
- `requirements.txt`、npm 锁文件、主要上游项目，以及本地已安装发行包的许可证。
- 使用临时数据复现“关闭 AI 后仍采集消息”；没有连接真实 QQ、调用真实模型或读取现有聊天档案。

这是源码检查与有限复现，不是完整渗透测试、全量漏洞扫描或全部代码来源鉴定。

## 公开前优先处理

### 1. 固定管理密码及历史记录

位置：[src/admin_auth.py](../src/admin_auth.py) 的 `DEFAULT_PASSWORD`、`_load_or_create()`、`_secret()`；[src/admin.py](../src/admin.py) 的登录接口。

初次启动会创建一个所有部署相同的默认密码，并将口令写到日志。密码明文保存在配置文件中，Cookie 签名密钥也由它派生；登录接口没有应用级限速。默认口令还存在于历史提交 `3d41283` 中，本记录不转载其内容。

**建议在公开前处理。** 新安装应强制显式设置密码，或使用每次安装独立的随机凭据；密码不写日志，密码存储改用合适的慢哈希，Cookie 使用独立随机密钥，并增加登录限速。已经使用过同一口令的部署应换口令；如果它在其他服务上被复用，也需要分别更换。

README 已给出启动前自行创建管理密码文件的临时做法，但没有消除源码中的问题。仅删除当前文件里的字面值也不会删除 Git 历史。是否清理历史、另建干净的公开仓库或保留历史，应由维护者决定，本次没有重写 Git 历史。

### 2. 文档含明确来源于真实日志的样本

位置：[NapCat 事件说明](Napcat事件JSON格式说明.md)。该文档明确写着“基于真实日志”，样本仍包含机器人 QQ、用户信息、昵称以及附件地址等字段。

这些内容尚未完成脱敏确认。公开前应逐项替换为独立构造的假数据，清除可能携带授权参数的附件地址和可关联到原消息的标识，不能只替换标题中的“真实日志”。历史提交中的旧样本也要一并考虑。

目前没有发现被 Git 跟踪的聊天数据库、图片、漫画 PDF、`.env`、`data/` 或凭据密钥文件提交路径；按常见模式扫描也未发现其他明显真实 API Key、refresh token 或私钥。这个结果不等于所有任意格式凭据都已经排除。测试邮件地址使用了保留的 `.invalid` 域名。

Git 作者邮箱、默认机器人网名和一些测试中使用的 QQ/群号也会随公开可见。应由维护者确认是否愿意保留这些个人关联信息。

### 3. QQ WebSocket 未认证，身份来自请求体

位置：[src/bot.py](../src/bot.py) 的 `handle_websocket()`、`handle_event()`；[src/main.py](../src/main.py) 的 `/ws` 路由。

连接建立前没有验证访问 token、签名或来源，事件中的 `user_id` 等字段直接用于生成上下文和主人判断。能连上这个入口的客户端可以伪造 QQ 身份；如果该身份被绑定为主人，后果会扩大到 Agent 的命令和工作区外访问。

Compose 与 systemd 模板的回环监听降低了暴露范围，但 Python 直接启动默认监听所有地址。应增加服务端验证的连接凭据，在完成前仅通过受控内网/回环连接，并限制来源。单独在 NapCat 填 token，不会让当前后端自动验证它。

## 需要明确的隐私和权限设计

### 4. 关闭功能不代表停止采集或停止所有模型调用

位置：[FeatureManager.handle_event()](../src/feature/manager.py)、[AiFeature.observe()](../src/feature/ai/feature.py) 及其 `_render()`。

管理器会在功能关闭时继续调用 `observe()`；AI 的采集过程没有相应的总停止判断。临时复现中将功能、聊天、记忆和自动学习全部关闭，仍生成了原始消息档案并调用内容转述流程。图片/PDF 分支还可能调用视觉 API，因此可能继续向外部服务发送内容并产生费用。关闭 OCR 也不等于关闭图片的视觉请求。

这与是否允许“后台持续收集”有关，属于需要明确选择的产品策略。建议提供独立的采集/媒体理解开关，并在界面说明开关实际影响；本次没有自行改变该策略。README 已如实注明现状。

### 5. 跨群和私聊只有发送/部分写入边界，没有读取隔离

位置：[ChatEngine._turn()](../src/feature/ai/engine.py)、[dsh/policy.mjs](../dsh/policy.mjs)、[记忆检索](../src/feature/ai/index.py)。

共享主对话会接收不同群和私聊的资料；普通任务的 read/glob/grep 可以读取整个工作区，`search_memory` 的 auto 范围也会查各类记忆。限制发送目的地、限制可写目录，以及提示词要求保密，都不能阻止资料先进入同一模型上下文。

这是既有共享设计，本次没有拆分。适合相互信任的使用者，不应描述为多租户隔离。需要对接陌生群、敏感私聊或多个互不信任的 QQ 账号时，应另行设计按场景分区的读取与上下文策略。

### 6. 主人命令权限不是完整的安全沙箱

位置：[dsh/policy.mjs](../dsh/policy.mjs)、[systemd 模板](../deploy/myqqbot.service)、[Dockerfile](../Dockerfile)。

主人任务可使用进程拥有的 OS 权限，读取工作区外内容并执行命令。共享资料和网页中的恶意指令仍可能影响模型判断；授权为主人不能保证模型执行的每个动作都符合主人的真实意图。Docker 镜像也没有显式设置非 root 的运行用户。

建议专用低权限系统账号、最少挂载与资源限制；危险动作可另设确认机制。不要把这套设计宣传为主人以外的任何输入都绝不可能影响服务器。本次没有调整主人能力范围。

### 7. 日志、下载地址和凭据仍需分别管理

- [src/bot.py](../src/bot.py) 会记录消息正文；主人绑定指令在进入绑定处理前也已经经过日志记录。原文 30 天清理不负责清理 systemd、容器日志和管理员自己的备份。
- [src/main.py](../src/main.py) 公开挂载 JM/Pixiv 文件目录，文件读取不经过 admin 登录。下载地址不是可靠的授权凭证，已知路径的内容可能被取得。应通过受控网络或带期限的下载授权提供文件。
- [PixivConfig](../src/feature/pixiv/config.py) 将账号加密，但密钥与密文都在 data 中。该做法不保护能读取整份 data 的人；refresh token 则保存在单独的配置文件中。备份和文件权限要一起保护。
- 群定时任务目前是“同群成员共同管理”，不是创建者独占管理。这个行为已在 README 说明；是否收紧权限属于另一个策略决定。

## 发布和维护方面的问题

### 8. 第三方复用已补标，但不能把全部制品标成 MIT

本次新增项目 MIT LICENSE、[第三方说明](../THIRD_PARTY_NOTICES.md)，以及 dsh、JM、gppt、PixivPy 的上游许可副本。

dsh 和 JM 的关键实现确实来自上游依赖，接入层代码不应掩盖这一点。另外核对到 `img2pdf` 的 LGPLv3、npm 间接依赖中的 LibreOffice kit 的 MPL-2.0、libvips/部分 sharp 平台包的 LGPL，以及镜像里的 Poppler 等非 MIT 组件。发布预装镜像前要检查实际镜像的第三方声明和适用要求，不能只放一个项目 MIT 就结束。

当前没有发现整仓上游源码内嵌；已确认的主要方式是包依赖与接口调用。历史教程引用了其他项目，但没有据此发现它们是当前运行依赖。对每一行示例的原创性没有作绝对保证。

### 9. 依赖版本、安装和测试还不够可复现

- `requirements.txt` 固定了较早的 FastAPI `0.109.0`，本地对应 Starlette `0.35.1`。该版本落在上游已公布的部分安全修复之前，例如 [multipart DoS 公告](https://github.com/Kludex/starlette/security/advisories/GHSA-f96h-pmfr-66vw)。当前接口以 JSON 为主，没有据此认定该 multipart 问题在本项目已经可利用；仍应安排兼容升级和实际依赖扫描，不能只看测试通过。
- Python 大量使用版本范围，没有发布用的完整锁文件；Docker 的 torch 安装还会在指定版本失败后回退到未锁定版本。npm 虽有锁文件，但包含比当前挂载插件更大的依赖集合。
- 没有发现 GitHub Actions 等 CI 配置；dsh 未安装时，真实内核测试会跳过。公开后应让 CI 明确安装 Node/dsh，并区分测试通过和关键测试被跳过。
- 关闭娱乐模块仍要安装其 Python 和浏览器依赖。建议后续分离可选依赖，减少不使用这些功能时的安装体积及维护范围。
- 文档中的历史开发指南和教程有过时的命令、功能列表和部署建议。新 README 已把它们与现行说明分开，尚未逐篇重写。

### 10. 成本、滥用与可选内容服务

QQ 事件队列、聊天队列及娱乐模块队列没有完整的全局容量/费用配额；后台 Spawn 的并发限制和每会话 1000 个定时任务上限不等于完整反滥用措施。多个群友可持续触发任务，需考虑资源、模型费用和发送频率。

JM、Pixiv 默认关闭且已有可用性自检，但网络、授权、风控和来源内容无法由本项目保证。JM 自检带有默认样本 ID，公开演示前应确认样本内容与使用权限，或改为管理员自行提供。不应把下载与转发功能描述为能获取、分发任何作品的授权。

## 已有的保护

项目已经具备一些有用的防护，不需要因此全部推倒重写：

- data、环境配置和 node_modules 已被 Git 忽略，本次也未发现这些路径曾被提交。
- 管理端数据路由有 Cookie 登录校验；QQ 与模型回调是两套不同入口，dsh 私有回调使用随机 token 并只监听回环地址。
- QQ 工具固定发送到真实请求场景，普通写入有用户/群/文件目录范围检查，附件下载有内网地址和重定向检查。
- 记忆整理使用暂存、冲突检查与可恢复提交，升级前有会话备份；发送回执未知时不自动重试。
- Pixiv 账号获取在独立进程中运行，有超时和自动重登冷却；管理接口不直接返回口令或 token。

这些保护各有范围，不能替代上面的默认口令、事件认证、隐私分区及资源限制。
