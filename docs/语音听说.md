# 语音听说

机器人继续用 DeepSeek / dsh 聊天，声音理解和语音合成由阿里云百炼提供。不下载本地语音模型，不需要 GPU，也不会在机器人容器中安装整套语音推理环境。

## 能做什么

- 听 QQ 语音条，也能分析作为文件发送的常见音频。
- 提取可辨认的原话，另外描述笑声、停顿、语速、环境声、音乐和歌声。
- 根据聊天内容生成口语化正文，用固定音色合成并发送 QQ 语音条；可单独控制说话方式。
- 把当前会话工作目录中已有的音频作为语音条发送。
- 在 AI 定时任务中合成并发送语音，例如每天早上的语音提醒。

声音描述是模型的分析结果，可能出错。它不能可靠识别说话人的真实身份、心理状态或歌曲名称；听不清时会注明不确定。音乐不会被刻意编成一段用户指令。没有做声音克隆，也没有实时通话功能。

## 配置与升级

在项目根目录的 `.env` 填写以下配置；使用 systemd 时放入服务实际加载的环境文件：

```dotenv
DEEPSEEK_API_KEY=自己的DeepSeekKey
DASHSCOPE_API_KEY=自己的百炼Key
DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
DASHSCOPE_HTTP_BASE_URL=https://dashscope.aliyuncs.com/api/v1
AI_AUDIO_MODEL=qwen3.8-omni-flash
AI_TTS_MODEL=qwen-audio-3.0-tts-plus
AI_TTS_VOICE=longanlingxin
AI_TTS_INSTRUCTION="用自然亲近的语气说话，像日常聊天，避免播音腔和夸张表演。"
```

上面是北京地域的默认地址。本次接入已用该地址完成实际合成和理解测试；如果你的百炼业务空间要求专属域名，或使用其他地域，请按控制台提供的地址分别设置兼容接口和原生 HTTP 接口。Key、模型和音色必须在对应地域可用；并非任意 Qwen 模型都能直接替换。

声音服务的 Key 只由 Python 宿主使用，不作为 dsh 子进程的环境变量传入，也不会通过 admin 配置接口返回。模型、音色和密钥只在部署环境中配置；admin 负责开关和测试。

Docker 部署更新代码和环境后运行：

```bash
docker compose up -d --build myqqbot
docker compose logs -f myqqbot
```

只执行 `docker compose restart` 不会加载改动过的 Compose 环境配置。已有 `data` 继续使用；启动时只为媒体任务表补充语音状态字段，并创建语音缓存，不重建聊天、记忆或 dsh 会话。

在 admin 的“AI 服务 → 账号与功能”中分别开启“云端声音理解”和“语音合成与 QQ 语音发送”。默认开启，但未配置 Key 时只返回明确的未配置状态。如果显式设置了 `AI_AUDIO_ENABLED` 或 `AI_VOICE_ENABLED`，对应环境变量优先于 admin 开关。

NapCat 需要能执行 `get_record` 的 WAV 转码，以及发送 `record` 消息段。转换由 NapCat 自己的音频组件完成；跨容器时通过 Base64 传回音频，不要求机器人能访问 NapCat 的磁盘路径。NapCat 的转码组件缺失或失效时，宿主会返回失败原因。

## 收到语音后如何处理

1. 立即保存原始事件与音频附件信息，将解析加入持久后台队列。主聊天继续接待其他消息。
2. QQ 语音通过 `get_record(out_format=wav)` 获取可播放数据；普通音频文件走已有的受限下载链路。
3. 内容相同且模型、分析提示词相同的音频复用缓存。尚未解析的音频调用 Omni，得到【语音原文】【声音观察】【不确定之处】。
4. 结果关联原消息，更新聊天转述，并作为同一旧消息的补充交给记忆维护，不多计一条人类消息。
5. 私聊、被 @ 的语音、原本处于活跃聊天窗口的语音在解析后进入主对话。普通群语音中的直接话语明确喊出机器人网名也能唤醒；文件名、声音观察和转发引用不会据此唤醒。

没有唤醒的群语音也会后台解析和记录。关闭声音理解可停止云端分析；已发出的云请求可能仍会完成。合并转发中的语音只作为引用资料，不赋予转发者新的指令权限。

执行者可用现有 `read_media` 查看音频处理状态和完整结果。后台任务持久保存，重启可继续未完成解析。网络、限流等暂时错误有有限重试；缺少 Key、无权限、格式不支持等确定错误不会无限重试，也不会捏造声音内容。

## 如何说话

可以直接对机器人说：“请用语音回复我，语气轻松一点。”也可以要求她“把刚才那段话用语音发给我”。

主对话调用 `spawn_task` 交给执行者，执行者调用：

```text
synthesize_voice(text="晚上好，今天辛苦啦。", instruction="温和自然，稍慢一点，像日常聊天。")
```

执行者把成功结果中的 `voice_id` 和正文返回主对话。主对话再调用：

```text
send_voice(voice_id="工具实际返回的ID")
```

`instruction` 描述表达方式，不能改变音色或密钥；正文中不要放需要被朗读成台词的舞台说明。生成成功只表示拿到了音频，收到 QQ 发送成功回执后才算交付。普通 Spawn 不直接发送语音；独立的定时任务分支可以自己合成再发送。`silent` 定时任务仍禁止所有 QQ 发送。

发送已有音频时使用 `send_voice(path="当前会话目录内的文件.wav")`，与 `voice_id` 二选一。接口只向当前群或私聊发送，不能传入其他群号，也不能发送其他会话缓存或直接导出服务器文件。工作区音频仍要求文件功能开启；发送本次合成的语音不依赖文件开关。

模型最终文本不会自动变成语音或 QQ 消息。发送超时、回执缺少消息 ID 等情况标为 `unknown`，禁止自动重复发送；任务被取消或功能关闭后也不再交付。

## 测试与排错

admin 的“AI 服务 → 语音听说”提供：

- 查看 Key 是否已配置、启用状态、模型、音色和最近错误；不显示 Key。
- 输入短文本合成试听，在浏览器播放，不向 QQ 发送。
- 上传音频测试理解，查看转写和声音描述，不进入聊天或记忆。

这两项测试会使用真实云服务并产生费用。若不方便打开 admin，可在项目根目录运行：

```bash
# 只检查配置状态，不调用云服务
python scripts/check_audio.py

# 合成一句测试文本，再用 Omni 分析这段音频；不发送 QQ 消息
python scripts/check_audio.py --live

# Docker 部署时
docker compose exec myqqbot python scripts/check_audio.py --live
```

`audio_auth_failed` 通常需要检查 Key 和接口地域；`audio_permission_denied` 需要检查模型授权、业务空间和账户状态；`audio_rate_limited` 需要检查额度或限流。`audio_download_failed` 需要结合情况检查 NapCat 转码、过期链接和部署网络。云端听说测试通过后，再用真实 QQ 客户端分别试一次接收语音和请求语音回复，确认 NapCat 转码与客户端播放正常。

## 存储、费用和限制

声音理解和生成都调用云服务，接收音频会上传到阿里云。原始事件、转写与声音描述沿用项目现有聊天/记忆规则；模型分析并不等于都要写成长期用户画像。声音理解缓存最长 30 天，结果随原消息的保留期限清理。

生成的音频放在 `data/ai/.state/voice-cache/`，元数据在同目录的 `voices.sqlite3`。音频最多保留 24 小时、200 份，总大小不超过 128 MiB，定期及写入时清理；包含在项目备份范围内。admin 上传测试的原音频不会另存为长期文件。云端返回的临时签名 URL 不交给 Agent 或 QQ。

单条输入最多 20 MiB，WAV 另限制为 5 分钟；压缩音频当前按文件大小限制，不承诺统一的时长上限。自动识别 WAV、MP3、M4A、Ogg/Opus、FLAC、AMR、AAC。损坏文件、特殊编码或云服务不支持的格式仍可能被拒绝。

一次语音合成最多 1200 字符，表达指令最多 500 字符，每个执行回合最多尝试两次合成；每个发送回合最多尝试两次语音发送。声音理解和合成各最多两个并行请求，重复内容复用结果。这些限制用于避免单个任务无限占用资源，并非全站每日费用上限。

接口说明参考 [Qwen Omni 官方文档](https://help.aliyun.com/zh/model-studio/qwen-omni)、[语音合成官方文档](https://help.aliyun.com/zh/model-studio/non-realtime-tts-user-guide)、[音色列表](https://help.aliyun.com/zh/model-studio/qwen-audio-tts-voice-list)和 [NapCat 文件处理说明](https://doc.napneko.icu/develop/file)。
